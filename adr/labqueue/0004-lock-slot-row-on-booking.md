# Блокировать строку слота при изменении очереди

## Контекст и постановка задачи

Когда открывается запись, много студентов одновременно претендуют на
последние места. Число активных записей не должно превышать вместимость, а
позиции не должны повторяться (REQ-REL-001).

## Драйверы решения

* корректность при гонке
* простота реализации и тестирования
* производительность одного слота

## Рассмотренные варианты

* SELECT … FOR UPDATE по слоту
* Оптимистичная блокировка с повтором
* Изоляция SERIALIZABLE

## Итог решения

Выбранный вариант: «SELECT … FOR UPDATE по слоту», потому что операции
одного слота становятся строго последовательными без повторов на клиенте, а
разные слоты обрабатываются параллельно.

### Последствия

* Хорошо, потому что детерминированный результат при гонке
* Плохо, потому что короткое ожидание блокировки при пике записи

### Подтверждение

Тест `ConcurrentBookingTest`: 50 параллельных запросов на одно место дают
ровно одну запись.

## Плюсы и минусы вариантов

### SELECT … FOR UPDATE по слоту

* Хорошо, потому что просто и надёжно
* Плохо, потому что сериализует операции одного слота

### Оптимистичная блокировка с повтором

* Хорошо, потому что нет ожидания
* Плохо, потому что повторы и всплеск ошибок при пике

### Изоляция SERIALIZABLE

* Хорошо, потому что гарантии на уровне СУБД
* Плохо, потому что частые откаты транзакций
