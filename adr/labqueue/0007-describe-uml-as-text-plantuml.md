# Описывать динамическое поведение LabQueue на UML текстом PlantUML и хранить рядом с PNG

## Контекст и постановка задачи

В лабораторной работе №5 нужно описать динамическое поведение системы: диаграммы прецедентов, активности, состояний и последовательности. Диаграммы должны меняться вместе с требованиями (в ЛР4 они уже менялись трижды), поэтому их нужно уметь сравнивать в Git и править без графического редактора. Как хранить UML-модель и как связать диаграммы между собой и с требованиями SRS?

## Драйверы решения

* изменения диаграмм должны быть видны в `git diff` и ревью pull request;
* единый источник правды: имена и подписи на рисунках совпадают с текстом;
* трассируемость: прецедент → требование SRS → диаграммы → тесты;
* бесплатный инструмент, работающий в репозитории без лицензий (CON-4, бюджет 0);
* рекомендация задания ЛР5 использовать текстовое описание UML.

## Рассмотренные варианты

* PlantUML: текстовые `.puml` и PNG рядом
* Графический редактор (draw.io, Visual Paradigm) с бинарными файлами
* SysML v2, как в ЛР3
* Mermaid в Markdown

## Итог решения

Выбранный вариант: «PlantUML: текстовые `.puml` и PNG рядом», потому что только он одновременно даёт читаемый `git diff`, полный набор нужных UML-диаграмм (прецеденты, активность с дорожками и fork/join, состояния с составным состоянием, последовательность с фрагментами alt) и не требует лицензии.

### Как строятся диаграммы и связи

1. **Источник** — файл `sdd/uml/<имя>.puml`. Имена участников, состояний и переходов совпадают с глоссарием `srs/glossary-labqueue.md`.
2. **Изображение** — `sdd/images/uml-<имя>.png`, его строит `sdd/uml/render_uml.py` (headless Chrome или Edge); перегенерация: `python sdd/uml/render_uml.py`.
3. **Цепочка построения:** SRS (требования) → прецеденты и их потоки событий (`sdd/uml/use-cases.md`) → диаграммы активности по основным потокам → диаграммы состояний по статусам, которые меняют потоки → диаграммы последовательности по самым сложным потокам.
4. **Связи на диаграмме прецедентов:**
   * коммуникация (сплошная линия) соединяет актёра с прецедентом, который он инициирует;
   * `include` (пунктир со стрелкой к включаемому) используется, когда поведение всегда входит в другой прецедент: UC-06 → UC-15, UC-15 → UC-17;
   * `extend` (пунктир со стрелкой к базовому) используется, когда поведение добавляется по условию: UC-05 → UC-04 при условии «мест нет», UC-10 и UC-11 → UC-09, UC-13 → UC-12;
   * связи между актёрами и обобщение актёров не моделируются, потому что актёры находятся вне системы и ведут себя по-разному только в отдельных прецедентах;
   * два прецедента не соединяются коммуникацией, так как диаграмма описывает доступные функции, а не порядок их выполнения.
5. **Системный актёр «Время»** запускает UC-16 и UC-17: от времени зависит запуск событий, поэтому он оформлен как актёр, а не как шаг потока.
6. **Диаграммы активности** используют дорожки по участникам (студент, система, планировщик), ветвление `if` и параллельные ветки `fork`/`join`; каждое действие соответствует шагу основного или альтернативного потока прецедента.
7. **Диаграммы состояний** содержат сигналы, сторожевые условия и действия (`событие [условие] / действие`), совпадающие с сигналами модели SysML `srs/models/booking.sysml`.
8. **Диаграммы последовательности** показывают линии жизни, полосы активации, синхронные сообщения и возвраты, фрагмент `alt` и сообщение самому себе; в том числе блокировку слота из ADR-0004 и outbox из ADR-0005.

### Последствия

* Хорошо, потому что диаграммы можно ревьюить построчно и менять вместе с кодом.
* Хорошо, потому что трассируемость требований и диаграмм проверяется поиском идентификаторов в текстовых файлах.
* Плохо, потому что PNG строится отдельным скриптом по заданной геометрии, и при изменении `.puml` изображение приходится обновлять вручную.
* Плохо, потому что для сложных диаграмм автоматическая раскладка PlantUML может потребовать подбора параметров.

### Подтверждение

На ревью проверяется, что каждое имя на PNG встречается в соответствующем `.puml`, а каждый прецедент из `use-cases.md` присутствует на диаграмме. В дальнейшем проверку можно автоматизировать шагом GitHub Actions, который строит диаграммы PlantUML из каталога `sdd/uml` и сравнивает их с PNG.

## Плюсы и минусы вариантов

### PlantUML: текстовые `.puml` и PNG рядом

* Хорошо, потому что текст сравнивается в Git и редактируется в любом редакторе.
* Хорошо, потому что поддерживаются все нужные виды диаграмм.
* Хорошо, потому что бесплатный и с открытым кодом.
* Плохо, потому что для PNG нужен Java или отдельный рендер.

### Графический редактор (draw.io, Visual Paradigm) с бинарными файлами

* Хорошо, потому что удобно рисовать мышью.
* Плохо, потому что бинарные и XML-файлы плохо читаются в `git diff`.
* Плохо, потому что Visual Paradigm требует лицензии.

### SysML v2, как в ЛР3

* Хорошо, потому что язык уже использован для структуры и макетов.
* Плохо, потому что задание ЛР5 требует диаграммы UML, а SysML v2 не даёт готовой нотации диаграмм активности с дорожками.

### Mermaid в Markdown

* Хорошо, потому что диаграммы отображаются прямо на GitHub.
* Плохо, потому что нет диаграммы прецедентов и дорожек активности нужного вида.

## Дополнительная информация

SDD, представления 015–021; описания прецедентов — `sdd/uml/use-cases.md`; глоссарий — `srs/glossary-labqueue.md`; дополнительные спецификации — `srs/supplementary-spec-labqueue.md`. Решение пересматривается, если команда начнёт хранить модель в SysML v2 целиком. Синтаксис файлов `.puml` в этой работе не прогонялся через PlantUML: загрузка инструмента не выполнялась, поэтому PNG построены `render_uml.py`.
