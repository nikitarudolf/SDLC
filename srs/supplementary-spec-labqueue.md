# Дополнительные спецификации LabQueue

Версия 1.0 · 10.11.2026 · Подготовил Рудольф Н. В., гр. 450501

Документ собирает требования, которые нельзя привязать к одному прецеденту: качество, ограничения и правила, общие для всей системы. Структура соответствует модели FURPS+ (функциональность, удобство использования, надёжность, производительность, сопровождаемость и дополнительные ограничения). Каждое требование ссылается на идентификатор из `srs/srs-labqueue.md` (версия 0.4) и на прецеденты из `sdd/uml/use-cases.md`.

## 1. Функциональность (общие правила)

| ID | Требование | Источник | Прецеденты |
|----|------------|----------|------------|
| SS-FUN-01 | Каждое действие проверяется на сервере по роли и принадлежности: студент работает только со слотами своих групп, преподаватель — только со своими слотами и дисциплинами | REQ-SEC-003 | все |
| SS-FUN-02 | Каждое изменение записи и очереди (создание, отмена, перенос, продвижение, вызов, отметка, вызов вне очереди) записывается в журнал: время, автор, слот, студент, действие, причина; записи журнала нельзя изменить | REQ-OBS-001 | UC-04…UC-11, UC-15 |
| SS-FUN-03 | Изменения очереди одного слота выполняются строго последовательно: транзакция начинается с блокировки строки слота | REQ-REL-001, ADR-0004 | UC-04, UC-05, UC-06, UC-09, UC-15 |
| SS-FUN-04 | Все даты хранятся в UTC и показываются в часовом поясе Europe/Minsk | REQ-PORT-001, REQ-INT-002 | все |
| SS-FUN-05 | Письма отправляются из таблицы outbox фоновой задачей; недоступность SMTP не отменяет запись и продвижение | REQ-REL-002, ADR-0005 | UC-02, UC-11, UC-14, UC-15, UC-17 |

## 2. Удобство использования

| ID | Требование | Источник | Прецеденты |
|----|------------|----------|------------|
| SS-USE-01 | Интерфейс на русском языке; даты в формате ДД.ММ.ГГГГ, время ЧЧ:ММ | REQ-INT-002, CON-6 | все |
| SS-USE-02 | Интерфейс корректно отображается при ширине окна от 360 до 1920 px; на узком экране таблица слотов превращается в карточки | REQ-INT-001 | UC-03, UC-07 |
| SS-USE-03 | Статус слота и записи обозначается цветом и текстом одновременно; контраст текста не ниже 4,5:1 | REQ-INT-003 | UC-03, UC-07, UC-12 |
| SS-USE-04 | При ошибке ввода или нарушении правила причина показывается рядом с полем или кнопкой, введённые данные сохраняются | REQ-INT-004 | UC-04, UC-05, UC-08 |
| SS-USE-05 | Основные действия преподавателя в живой очереди выполняются одним нажатием | REQ-FUNC-012 | UC-09, UC-10, UC-11 |
| SS-USE-06 | Перед записью студент обязательно подтверждает, что запись аннулируется при неявке в течение 5 минут после вызова | REQ-FUNC-020 | UC-04, UC-05 |

## 3. Надёжность

| ID | Требование | Источник | Прецеденты |
|----|------------|----------|------------|
| SS-REL-01 | При 50 параллельных запросах на последнее место создаётся ровно одна запись | REQ-REL-001 | UC-04 |
| SS-REL-02 | Письмо при ошибке SMTP повторяется до 3 раз с интервалами 1, 5 и 15 минут, после чего ошибка пишется в журнал | REQ-REL-002 | UC-17 |
| SS-REL-03 | Перенос записи атомарен: исходная запись сохраняется, пока не получена новая | REQ-FUNC-008 | UC-06 |
| SS-REL-04 | Доступность в учебные часы с 08:00 до 21:00 по будням не ниже 99 % | REQ-AVAIL-001 | все |
| SS-REL-05 | Резервная копия базы создаётся ежедневно и хранится 14 дней; восстановление занимает не более 1 часа | REQ-AVAIL-002 | — |

## 4. Производительность

| ID | Требование | Источник | Прецеденты |
|----|------------|----------|------------|
| SS-PER-01 | 95 % запросов страниц и операций записи обрабатываются не дольше 1 с при 200 одновременных пользователях | REQ-PERF-001 | UC-03, UC-04 |
| SS-PER-02 | Изменение очереди отображается у всех клиентов слота не позже 10 с; при 60 клиентах опрос раз в 10 с не нагружает сервер за счёт ответа 304 по ETag | REQ-PERF-002, ADR-0003 | UC-07 |
| SS-PER-03 | Продвижение из листа ожидания выполняется в течение 1 минуты после освобождения места | REQ-FUNC-010 | UC-15 |

## 5. Сопровождаемость и реализация

| ID | Требование | Источник | Прецеденты |
|----|------------|----------|------------|
| SS-SUP-01 | Правила очереди (вместимость, позиции, ETA, продвижение) реализованы в модуле `queue` без зависимостей от веб-слоя и Spring | REQ-MAINT-001, ADR-0001 | UC-04, UC-15 |
| SS-SUP-02 | Покрытие модульными тестами модуля `queue` не ниже 80 %, проекта — не ниже 60 % | REQ-MAINT-002 | — |
| SS-SUP-03 | Приложение запускается одной командой `docker compose up`; миграции схемы применяются автоматически | REQ-INST-001, REQ-INST-002 | — |
| SS-SUP-04 | Сборка выполняется Maven на JDK 21; каждый pull request проверяется в GitHub Actions | REQ-BUILD-001, REQ-BUILD-002 | — |

## 6. Ограничения проектирования

| ID | Ограничение | Источник |
|----|-------------|----------|
| SS-CON-01 | Серверная часть — Java 21 и Spring Boot 3.x | CON-1 |
| SS-CON-02 | Клиент — веб-браузер без установки ПО; страницы формируются на сервере (Thymeleaf) | CON-2, ADR-0002 |
| SS-CON-03 | СУБД — PostgreSQL 16 | CON-3 |
| SS-CON-04 | Уведомления только по e-mail (SMTP) и в приложении; платные сервисы не используются | CON-4 |

## 7. Безопасность и правовые требования

| ID | Требование | Источник | Прецеденты |
|----|------------|----------|------------|
| SS-SEC-01 | Пароли хранятся только в виде хеша BCrypt (cost не ниже 10); весь трафик идёт по HTTPS (TLS 1.2+); cookie сессии — HttpOnly, Secure, SameSite=Lax | REQ-SEC-001 | UC-01, UC-02 |
| SS-SEC-02 | После 5 неудачных попыток входа подряд вход блокируется на 15 минут | REQ-SEC-002 | UC-01 |
| SS-SEC-03 | Все изменяющие запросы защищены CSRF-токеном; запросы к базе — параметризованные | REQ-SEC-004 | все |
| SS-SEC-04 | Студент видит других студентов в очереди только как «Фамилия И.» без e-mail и группы | REQ-SEC-003 | UC-07 |
| SS-SEC-05 | Обработка персональных данных соответствует Закону РБ № 99-З: согласие при регистрации, политика конфиденциальности, удаление учётной записи по запросу | REQ-COMP-001 | UC-02 |
| SS-SEC-06 | Используются только библиотеки с лицензиями, допускающими бесплатное использование (Apache 2.0, MIT, BSD, LGPL) | REQ-COMP-002 | — |
